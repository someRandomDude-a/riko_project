# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Riko is a local desktop AI companion with a VRM avatar.
- **Python backend** (`Code/`, FastAPI/uvicorn on `127.0.0.1:8765`, or `RIKO_PORT`) owns conversation, in-process llama.cpp inference, microphone capture/ASR, TTS playback, memory, tools and persistence. Core package: `Code/process/app_core/` (written `app_core/` below). Entry points: `Code/run_server.py` (backend), `Code/desktop_server.py` (`create_app`; the routes are in `app_core/http/`), `Code/discord_bot.py`, `Code/task_mcp_server.py`.
- **Electron + React + three.js** (`electron/`) owns every window, the avatar and the UI, and talks to the backend only over HTTP/WebSocket.

This layout is on `main` (formerly the `rewrite-2` branch). `origin/llama.cpp` is an older pre-rewrite tree, kept for reference, whose tip fails to parse (`Code/process/llm_scripts/module.py:238`). `old llm_scripts/` here is dead code (the space in its name makes it unimportable).

### Native llama.cpp bridge

`tools/llama_cpp/README.md` (PowerShell-oriented) is the reference. Check out llama.cpp at `b92761a515ea31e852e7fbc1fad5f874b46f3718`, run `git apply --check` and then `git apply` with `tools/llama_cpp/emotion-probe.patch`, then:

```bash
cmake -S .native/llama.cpp -B .native/llama.cpp/build -DGGML_CUDA=ON -DLLAMA_BUILD_TESTS=OFF -DLLAMA_BUILD_EXAMPLES=OFF -DRIKO_NATIVE_BRIDGE_SOURCE="$PWD/tools/llama_cpp/riko-native.cpp"
cmake --build .native/llama.cpp/build --config Release --target riko-native -j 2
```

`-DGGML_CUDA=OFF` gives a CPU-only build on Windows/Linux. On macOS the same configure builds Metal by default (embedded shader library, no full Xcode needed) and produces `libriko-native.dylib`. On Linux with ROCm, `HIPCXX="$(hipconfig -l)/clang" HIP_PATH="$(hipconfig -R)"` before the configure and `-DGGML_HIP=ON -DGPU_TARGETS=<gfx name> -DGGML_BACKEND_DL=ON` in place of `-DGGML_CUDA=ON` build HIP (the full command is in `tools/llama_cpp/README.md`). Point `runtime.native_library` at the built library and keep its llama/ggml libraries beside it; `python tools/release/build.py --smoke-bundle <backend> <clean checkout at the pin> <folder>` builds such a self-contained folder exactly as a release does. A static Linux configure (`BUILD_SHARED_LIBS=OFF`) needs `-DCMAKE_POSITION_INDEPENDENT_CODE=ON` (the patch refuses it otherwise), and `riko-native` gets an `$ORIGIN`/`@loader_path` install rpath unless `CMAKE_INSTALL_RPATH` is set.

`riko_create` loads ggml's backends from the bridge's own folder (`dladdr`/`GetModuleHandleExW`) before `llama_backend_init` when none are registered, i.e. in a `GGML_BACKEND_DL` build, whose backend modules ggml itself seeks only beside the executable and in the cwd; on Windows it preloads each module with `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR` so cudart/cuBLAS resolve beside it. A GPU module that does not load (no Vulkan loader, no ROCm for `ggml-hip`) or finds no device leaves llama.cpp on the CPU with a `riko-native: no GPU device from ...` note, which the provider logs as a warning. `riko_devices` (the sixth export) reports ggml's devices with free and total memory as JSON into the caller's buffer; it is valid after the first `riko_create` (even a failed one), returns -2 before it, and Metal's figures are this process's working set (`recommendedMaxWorkingSetSize`), not the GPU's.

Release (CI only, `.github/workflows/release.yml`): Python dependencies come from the hash-locked `tools/release/requirements-lock*.txt` (CPU torch; PyInstaller pinned there), and Electron's from `electron/package-lock.json` via `npm ci` (only `yaml` is a runtime dependency; electron and electron-builder 26.0.12 are exact devDependencies). `python tools/release/build.py` clones llama.cpp into `.native/llama.cpp-release` (it refuses if that exists), builds the `cuda` (with `GGML_CUDA_NO_VMM`, so no hard link to the NVIDIA driver) and `vulkan` backends, freezes `riko-backend` with PyInstaller (its output moved, not copied, into `release-stage/backend`; the build refuses to run over an earlier `release-stage/` or `release-build/`, keeps each library once with its versioned links, which electron-builder's extraResources copy preserves, and ships `tools/release/NOTICE.md` to users) and runs `riko-backend --release-check <library>` in a cleaned environment: it checks the six exports (`riko_devices` included) and prints ggml's devices, that bundled libraries load from the bundle and no driver library loads with it, calls `riko_create` without arguments (it initialises the backends and fails before a model) and, for a `GGML_BACKEND_DL` bundle, requires a CPU module loaded from the bundle and every module to load from there, imports every lazily imported module and builds the app (`desktop_server.create_app` over an empty data root), runs a calculator call through the real `--tool-worker`, dry-runs the Discord worker, and asks `--setup-config` for a first-run configuration. electron-builder then packages from `electron/`. ROCm (HIP) is opt-in: a manual run with the `hip` input adds a job in the digest-pinned `rocm/dev-ubuntu-22.04:7.2.1` container (`.github/actions/hip-bundle`: `build.py --smoke-bundle hip`, then `build.py --check-bundle`, which loads it against ROCm without a GPU), whose bundle the Linux leg stages from `RIKO_OPTIONAL_BUNDLES` and release-checks without ROCm (`system_libraries` may be missing there); tag pushes never build it. Every `uses:` in the workflows is a full commit SHA with its release tag in a comment (one commit per action repository; `tests/test_ci_workflows.py`), and both Vulkan SDK downloads are checked against LunarG's published SHA-256 (`VULKAN_SDK_*` in release.yml's package job) before they are extracted or run; the Windows CUDA network installer that Jimver/cuda-toolkit fetches is still unverified (NVIDIA publishes only MD5). Windows installers are unsigned; `tools/release/README.md` has the signing plan (Azure Trusted Signing or a cloud-HSM OV certificate, `SHA256SUMS` and build-provenance attestations).

## Architecture

### Process model
- **Dev:** backend and Electron start separately; Electron never starts or stops Python. **Packaged:** Electron spawns and stops the frozen backend.
- Python child processes: a fresh interpreter per built-in tool call (`app_core/tools/worker.py`, `--tool-worker` when frozen), stdio MCP servers from `mcp.json`, and the Discord client (`--discord-worker` when frozen). `run_server.main` dispatches those worker flags before uvicorn or the config loads (`uvicorn`, `Server` and `load_config` are lazy module attributes there). GPT-SoVITS is always a separate HTTP server.
- Every Electron window loads the same Vite bundle, routed by URL hash in `electron/src/main.jsx`: `#/overlay` (transparent click-through avatar layer), `#/control` (chat/settings; "closing" collapses it to a dock), `#/whiteboard`, `#/effects`, `#/setup` (packaged first run), `#/neural-data`.
- `electron/main.cjs` is wiring only; each concern is a module built with Electron's objects (and timers) injected: `backend_supervisor.cjs` (origin, secrets, token injection, `request`, packaged spawn/stop, GPT-SoVITS), `window_manager.cjs` (window options, the chat full/compact/collapsed and whiteboard full/collapsed mode machines with their bounds, surface sync, overlay input, the gesture loop from `window_gesture.cjs`), `window_platform.cjs` (Win32 button hooks, Linux cursor forwarding, acrylic, the Wayland relaunch), `ipc_router.cjs`/`ipc_routes.cjs`, `tray_shortcuts.cjs`, `desktop_telemetry.cjs` and `avatar_assets.cjs`. `window_layout.compactSize` is the one dock/mini-chat size rule (mode switch, resize gesture and `compact-scale`).
- One `electron/preload.cjs` exposes every `contextBridge` API to every window, so main registers IPC only through the table in `electron/ipc_routes.cjs` (`{channel, from, handler}`), and `ipc_router.cjs` answers only when `event.sender` is a live window the route names (an invoke from anyone else rejects, a send is dropped). A new channel goes in that table and in the written-out owners of `src/ipc_routes.test.mjs`; `src/main_wiring.test.mjs` checks that the preload and the table name the same channels and that every other window is refused on each.

### Startup and service assembly
- `run_server.main` chdirs to `$RIKO_DATA_DIR` (default: repo root) and exports it for every child, loads config once (`load_config(recover='setup')`), configures logging, then passes that config to `desktop_server.create_app(config, services_factory=create_chat_service)`. Importing `desktop_server` does nothing; `create_app` (`app_core/http/app.py`) builds no service and reads no file: it makes the app's `Backend` (`app_core/http/backend.py`, `app.state.backend`: the config, the desktop state from `factory.create_desktop_state(config.paths)`, which reads nothing yet, the services the lifespan fills in or `startup_error`, and its own `DiscordLauncher`, `GPUMonitor`, `WhiteboardImages`, `Confirmations` and secrets), the routers (one module per URL domain under `app_core/http/`, Discord's in `integrations/discord/api.py`), which read the Backend through the `Services` dependency, never module globals, and the lifespan. `desktop_server.app` (and its old `stop_turn`/`api_secrets`) still builds one app on first use, for one release. Tests build an app per test (`tests/conftest.py`: the `backend` fixture, `client_for`, `build_backend`, with stub `services_factory`, `session_factory` and `initiative_factory` set on the Backend), never patch the module.
- The FastAPI lifespan calls `services_factory(config, desktop_state=state)`, i.e. `create_chat_service` (`app_core/factory.py`), which builds everything inside an `ExitStack` that rolls back on failure: `ActionController` → optional Julia emotion engine → `create_provider` (+ the optional emotion probe's `ProbeHook`, attached before the model loads) → `provider.warmup()` (loads the GGUF, no timeout) → `TaskStore` / `ToolRegistry` → `MemoryStore` (reflection lane, `capabilities.background_parallelism`, the provider's `count_text_tokens`, and the emotion engine's Julia `load_options` when strict encoding and equal `max_length` let System 1 share its model) → `ChatService`, which gets the factory's collaborators as a frozen `ChatDeps` (action controller, task store and MCP, initiative lane, live `context_limit`, emotion worker, `DesktopServices`) and whose `close()` owns the ExitStack. Then come `SessionManager`, `warm_session` (ASR/VAD/wake/TTS, bounded by `runtime.startup_timeout_seconds`), `ConversationStore`, the saved board (`WhiteboardModel.load`) and avatar geometry (`SurfaceGeometry.load_settings`; nothing is saved to either before it is read), `Initiative` and the resource/task-file watchers, and finally `runtime.ready` is published.
- `run_server.py` binds 127.0.0.1 on `RIKO_PORT` (1024–65535, default 8765; `backend_port` in `app_core/desktop/api_guard.py`) before the model loads (retrying for 20 s while a previous backend exits) and mints the API secrets right after; connections queue until lifespan startup finishes, so requests hang rather than fail while the model loads.
- With `desktop.setup_on_startup_error: true`, a section `load_config` cannot read (`load_config(recover='setup')`, used by both entry points, loads it with its defaults and lists it in `load_errors`; Settings' snapshot uses `recover=True`, validation stays strict), a failing `create_chat_service` or a failing `SessionManager` construction (the loaded chat is closed first) leaves only the settings/status/resource/media routes up (the rest return 503) so Settings can repair the YAML.
- Shutdown: `run_server.Server.shutdown` first cancels the active turn (`Backend.stop_turn`, bounded 1 s), then uvicorn drains for 2 s; the lifespan stops Discord in parallel with `close_bounded(session, 8)` (`app_core/kernel/lifecycle.py`; a hung close is abandoned to a daemon thread) → unwind the ExitStack. An atexit guard in `llama_native.py` destroys live native contexts, or `os._exit`s when one cannot be destroyed, because ggml-metal's static destructor aborts on leftover Metal buffers. The whole sequence stays under Electron's 15 s.

### Threading and events
- `event_bus` (`app_core/events/bus.py`) is synchronous: listeners run on the publisher's thread, their exceptions are swallowed, and every event carries a monotonic `sequence`.
- `SessionManager` (`app_core/runtime/session.py`) serialises foreground turns with a `TurnGate` (`app_core/kernel/turns.py`; `present_initiative` only tries it). A second turn raises `TurnBusy` (`app_core/kernel/cancellation.py`, a `RuntimeError` keeping the old message `'Riko is already handling another turn'`), which every route (`/api/chat`, `/ws/chat`, `/api/discord/chat`) maps to 409 by type, never by text; voice turns instead wait for the gate (`respond(wait=...)`, which raises `TurnCancelled` when the session closes or `wait()` turns true). Input is recorded in `DesktopState` only once the turn is taken. The `_voice_lock` RLock guards voice/playback state, and bus listeners can take it. Lock order is `_capture_lock` (request handlers only) → `_voice_lock` → component locks. **Never publish or run callbacks while holding a component lock**: queue them on an `Outbox` (`app_core/events/outbox.py`) and call `flush()` after releasing it. `tests/test_lock_discipline.py` enforces this with a static scan and deadlock regressions.
- Busy and idle have one definition: `SessionManager.status()` returns a frozen `RuntimeStatus` (`kernel/turns.py`; read under `_voice_lock`, or with `locked=False` from a callback that may run under a provider or tool lock, such as initiative's cancel poll and the probe's `provider.expression_idle()`, which SessionManager sets with `set_expression_idle`), and its predicates (`replying`, `local_reply`, `is_quiet`, `idle_for_background`, `model_state`) serve the avatar, wake feedback, initiative, the emotion probe, the calibration guard and `voice_anchor`. Other modules use only public session methods: `status()`, `is_open`, `active_turn()`, `cancel_turn(turn_id)` (Discord's `/stop`), `set_user_speaking()` (VoiceInput's VAD), `transcribe(pcm)` and `history_snapshot()`; `tests/test_session_surface.py` fails on any reach-in. Collaborators are passed, not patched on: `ChatService` takes `ChatDeps` and, per turn, a `TurnContext` (`kernel/turns.py`: origin, runtime observation, memory context, `emotion_from_playback`); desktop tools take `DesktopServices` (`desktop/tools.py`: the board, geometry and effects components they change, built with `DesktopServices.of(state, ...)`, plus their collaborators; SessionManager attaches `avatar_motion`); the probe asks `EmotionWorker.playback_active`. `ChatService`, `DesktopState` and `RuntimeConfig` have `__slots__`, so setting an undeclared attribute fails (`tests/test_declared_attributes.py`, which also bans `getattr` defaults for the retired names). Providers are used only through their declared members (Inference, below). `tests/test_private_access.py` pins every cross-object `_name` access (direct or through `getattr`/`setattr`/`hasattr`/`delattr` with a literal name) in app_core and `Code/*.py` per file, so a new one fails (and a removed one must be dropped from its list).
- Background work uses `DaemonExecutor` (`app_core/kernel/workers.py`; bounded queue, daemon threads). Each turn is cancelled through its own `threading.Event` and `TurnCancelled`; preempted background inference raises `BackgroundPreempted` (memory's `ReflectionDeferred` subclasses it). Both live in `app_core/kernel/cancellation.py` and derive from `Deferred` (stopped on purpose, not failed).

### Inference
- The provider contract is `inference/provider.py`: `InferenceProvider` (generate, stream, `count_tokens`/`count_text_tokens`, warmup, `cancel` (the live request only), `set_foreground`, `set_pause_background`, `set_expression_idle`, close, `lanes` (live, initiative, reflection) and `capabilities`, a `ProviderCapabilities(slots, exact_tokens, latent_probe)`). `BaseProvider` defaults every member but generate (one lane for every role, estimated counts, no-op lifecycle), every provider and test fake subclasses it, and no caller `hasattr`/`getattr`s a provider (`tests/test_provider_contract.py` scans for it). The probe's members are behind `provider.probe_host`, a `ProbeHost` (only `InProcessLlamaProvider`; else None): `attach_probe(hook, interval)`, `probe`, `probe_error`, `replay_lane`, `set_probe_interval`, `probe_idle`. Each generation notifies the provider's `GenerationObserver`s (`on_start`/`on_event`/`on_finish` with a `Generation`: role, slot, group, packed messages; a failing observer is logged and never fails the request). `emotion/probe_hook.py`'s `ProbeHook` is the observer that parses `riko.emotion_probe.sample` and the one home of `FEATURE_VERSION`/`FEATURE_WIDTH` (the patch repeats the version; `tests/test_release_build.py` compares them), so inference/ imports nothing from emotion/.
- The probe starts after the model has loaded, in its own `try`: a stale library (`/props` reporting another `FEATURE_VERSION`), missing torch, a Julia load failure or an unreadable file leaves the model up with `probe` None and `probe_error` set, which `/api/neural/status` returns; restart Python to retry. Its identity's GGUF and library fingerprints are cached per process by each file's (path, size, mtime) (`llama_context.fingerprint`), and its keys and values name existing probe data, so never change them. `EmotionProbe` reads Julia only through `ensure_loaded()`, `question_set()`, `resolved_source` and `fingerprint()`, and `EmotionProbe.replay(examples, lane)` runs `/api/neural/replay` on `replay_lane`.
- Julia-1 ships the Python package that loads it, so `emotion/teacher.py` is the one loader for the emotion engine and memory's System 1: `snapshot()` downloads at a full commit (`emotion.revision`, `memory.system1_revision`, default `JULIA_REVISION` in `kernel/model_pins.py`; a branch or tag is refused, and both settings are security-sensitive; when the Hub fails or is offline it retries with `local_files_only=True`, since a commit's snapshot otherwise needs huggingface_hub's `trees/<commit>.json` listing), `verify()` requires the pinned commit's `julia/**/*.py` to match `JULIA_CODE_SHA256` (another commit runs with a warning; `emotion.model_path`, the user's own folder, is not checked), `runtime()` imports the package as `riko_julia_<digest of the folder>` without touching `sys.path` or `sys.modules['julia']`, through `_Snapshots` (a `sys.meta_path` finder for `riko_julia_*` names only) that serves only the manifest's files and compiles each from the bytes whose SHA-256 it checks again (never `__pycache__` or other bytecode, a sourceless package folder, an extension module or an unlisted file, and no bytecode is written; an unchecked folder runs its `.py` files as hashed at first import), and `shared_model()` loads one model per (folder, device with MPS as CPU, options), once even when both warmups race, held weakly so `close()` still frees it. `resolved_source` stays the `snapshot_download` folder, so the probe identity is unchanged. Moving the pin means recording the new commit's file hashes (the module docstring says how).
- `create_provider` (`app_core/inference/providers.py`) picks the provider:
  - `llama_cpp` → `InProcessLlamaProvider` (`llama_native.py`). It calls the C ABI in `tools/llama_cpp/riko-native.cpp` via ctypes: six `riko_*` exports (`riko_devices` is optional at runtime: an older bridge lacks it, `NativeRuntime.devices()` answers None and telemetry falls back; `provider.devices()`, `BaseProvider`'s None, is the only way callers ask), serving only `/v1/responses`, `/apply-template`, `/tokenize`, `/props` and `/slots`, with argv from `native_arguments` in `llama_context.py`. There is no HTTP listener, llama-server or llama-cpp-python, and no fallback: `runtime.native_library` is required.
  - `llama_server` → `LlamaServerProvider` (`llama_server.py`): the same `LlamaContextProvider` protocol (slot 0 for live, exact `/apply-template` + `/tokenize` counts, `/v1/responses` streaming and tools) against a llama-server the user runs at `runtime.base_url` (default `http://127.0.0.1:8080`; validated by `server_address` in `llama_runtime.py`). It uses `http.client`, one connection per request, and cancels by shutting the socket down (closing alone does not wake a read blocked during prefill). Startup waits on `/health` (503 while loading), then requires exactly `parallel_slots` slots each holding the largest of the live, initiative and reflection budgets, and prints the matching `llama-server` command otherwise; a connection failure resets it so the next request checks again. The server owns the model and GPU settings, and there is no emotion probe.
  - `openai`, `lm_studio`, `openai_compatible`, `ollama`, `local_http` → `OpenAIProvider`: Responses API with a Chat Completions fallback, calibrated token estimates (`context_budget.estimate_tokens`, roughly 1.2-1.5x real counts), no slots. Stop is per request: `cancellable_stream` makes the request on a helper thread and shuts its socket down when the turn's `cancelled()` turns true (initiative and reflection share the provider, so there is no provider-wide cancel). Both provider families fold mid-conversation system messages with `responses.template_messages` (strict chat templates reject a later system message), which also joins consecutive user (or plain assistant) messages, because history keeps the user's message of a stopped, failed or unheard turn and Gemma/Mistral templates require alternating roles.
- `SlotScheduler` (`llama_context.py`) reserves slot 0 for the `live` lane. `initiative` and `reflection` share slots 1..N-1 (`runtime.parallel_slots`, 2–4), at most one `initiative` at a time (`kv_budget.suggested_pool` sizes a unified KV pool for one, and an overflow aborts every slot), and live turns preempt them when `runtime.pause_background_on_live` is set. The emotion probe captures only on slot 0; `probe_replay` (example replay) takes slot 0 only while no live request wants it, a foreground turn or a queued live request preempts it whatever that setting says, and `cancel_live` (Stop) reaches only a `live` lease.
- `--ctx-size` comes from `kv_budget.pool_capacity`. `runtime.flash_attn` is `auto`/`on`/`off` (YAML booleans mean on/off); `n_gpu_layers` -1 lets llama.cpp `--fit` keep 1 GiB free, -2 requires every layer, and only -1 passes `--fit on`. `split_mode: row` loads but the native provider refuses it. Budgets above the GGUF's training context fail before loading, and `riko_create` returns llama.cpp's own WARN/ERROR lines on failure and its offload/flash-attention notes on success. Per-role budgets are enforced only by Python-side packing (`context_budget.pack_context`, with exact native token counts) and by `max_output_tokens`. `pack_context` keeps an anchor per `ChatService` (`context_state`) so a steady turn costs one count and the history prefix stays stable between trims (trim to 3/4 of history's room, re-expand below 1/2); as a last resort it truncates oversized tool results with a marker. The tool loop adds a runtime observation only when the runtime state (not its timestamp) changed and keeps the ones it sent, so each tool-loop request extends the previous one; memory captures store a bounded `formation_context`, and `task_get` returns a summarised, limited change history.
- Turn flow: `SessionManager.respond` → `ChatService.respond` (`app_core/conversation/chat.py`):
  1. memory capture and recall (recall reaches the model as one JSON object per memory under `MEMORY_FRAME`, framed as untrusted data like the runtime observation: memories quote users, Discord and tools);
  2. the prompt: a stable system + history prefix (so the KV cache is reused), then `context_kind='optional'` system messages;
  3. `provider.generate`, which streams deltas;
  4. the `ToolRegistry` loop, up to `tools.max_iterations`;
  5. commit the turn to `chat.conversation`, which SessionManager then rewrites for speech over the reply or a cut.
- The native context is allocated once, so changing `n_ctx`, `parallel_slots`, the KV pool or the initiative/reflection budgets needs a Python restart. A native crash kills the whole backend.
- The llama.cpp pin and the patch's five-file footprint are enforced by `tests/test_release_build.py`.

### Voice pipeline
- The mic opens only on `/api/voice/start|activate` or `/api/mic/toggle`. `VoiceInput` (`app_core/audio/voice_input.py`) runs these threads:
  1. `microphone-capture`: sounddevice, 16 kHz mono int16, 512-sample frames.
  2. `voice-vad`: Silero VAD, `WakeWord` (EfficientWord-Net ONNX on CPU; an enrolled profile keeps its own calibrated threshold, which overrides `voice.wake_threshold`) and `VoiceSegments`. The wake phrase is `voice.wake_word`, else the first word of `presets.default.name`; an unusable one (several words, not text) disables only wake detection (`WakeWord.unavailable`, reason in wake status), never startup.
  3. `voice-asr`: faster-whisper through `session.transcribe`: the session's one model (`AsrService` in `app_core/audio/asr.py`, built once and shared with startup warmup and Discord's `/transcribe`).
  4. `voice-turn`: calls `SessionManager.respond`. `SessionManager.voice_transcript` returns a disposition that `VoiceInput` acts on: `fresh` (a new turn: no spoken reply in flight, a remote `speak=False` reply, a stale anchor, or a reply already finished or stopped), `reply` (the words were merged into the input or inserted as `[speaking over you]` at the cut, and the cut reply is redone with `record_user=False, reply_to=<turn>`; if another turn ran first, the redo takes those words back out of the cut turn's history and asks them as a new turn, so they are recorded once), `preserved` (tolerated speaking-over) or `ignored`.
- Output: streamed deltas → `SpeechChunks` (`speech.max_words`) → `SpeechQueue` (`app_core/audio/speech.py`) → GPT-SoVITS over HTTP (`sovits_ping_config.url`) → raw PCM16 played by sounddevice. `sovits_ping_config.sample_rate` must match the server.
- Barge-in uses the character offsets of spoken chunks. `Interjections` cancels after `voice.interruption_seconds`, and history is rewritten at the estimated cut point. `speak=False` turns (Discord) never engage the wake window or anchor local speech.
- There is no echo cancellation, so through speakers her echo is speech: in `voice.barge_in: full_duplex` (the default, behaviour unchanged) it can interrupt her and be saved as `[speaking over you] <her words>`. `audio/echo_gate.py` adds two opt-in half-duplex policies. `SpeechQueue.playback` (a `PlaybackLevel`, leaf lock) records each block `_write_audio` and `_play_clip` write (RMS of the scaled PCM, from the write until `output.latency` + its duration, with its run: the turn id, or the cue), and `VoiceInput` asks one `EchoGate` per frame: `stop_only` ignores the microphone while any block may sound (plus `voice.echo_tail_seconds`); `echo_gate` counts a frame only when VAD reaches `max(vad_threshold, barge_in_vad_threshold)` and its RMS is at least `MARGIN` (2) times her echo level times her level (each block in full from its write until certainly played, then fading 30 dB over the tail). Her echo level is `voice.echo_coupling`, else learned afresh for every run (reply or cue) from its first 64 frames of her speech (`echo_level`: the 90th percentile of microphone/her level, at most twice the median), acting as `stop_only` until then, or using the last reply's level once the median of 32 frames shows this echo is no louder; so a speaker, headphone or volume change counts from the next reply, not within one. In a model of the blocking writes with real Silero VAD, checked in real time through the real voice path (`MARGIN`'s comment has the numbers), one echo frame passed in 140 runs with correctly reported latency, and a user needed about 4-6 times her echo's RMS for 2-3 s; an under-reported output latency (Bluetooth) can leak a few frames (`echo_tail_seconds` helps), and raising the volume 6 dB or more mid-reply lets her echo through until the next reply. A frame judged echo reaches the wake detector and segmenter as silence, so her words never become an utterance or pre-roll, and in these two modes `VoiceInput` never transcribes an utterance with under `MIN_VOICED` (.2 s) of speech among gated frames (Whisper turns such fragments into "you"); `full_duplex` never reads playback. The proper fix is AEC with the exact PCM `_write_audio` writes (after `scale_pcm16`) and the float blocks `_play_clip` writes as the far-end reference, resampled to 16 kHz and aligned through callback or full-duplex sounddevice streams (PortAudio's `outputBufferDacTime`/`inputBufferAdcTime`): WebRTC APM AEC3 (10 ms frames, so the 512-sample frames are rebuffered; e.g. LiveKit's `AudioProcessingModule`), speexdsp (`speex_echo`, about 256 ms filter, lighter but weaker on laptop speakers) or macOS VoiceProcessingIO (`AVAudioEngine` voice processing, which needs playback through the same engine: a native helper); on Linux, PipeWire/PulseAudio `module-echo-cancel` as `voice.input_device` works today. The gate would stay behind AEC as a residual-echo guard.

### Persistence
The data root is the directory holding `character_config.yaml`. Every location comes from `AppConfig.paths`, a frozen `DataPaths` (`app_core/configuration/paths.py`) that `load_config` builds once, honouring `memory.history_file` (or a top-level `history_file`), `memory.store_file` and `tasks.store_file` (now with `~` expanded; a store already in the literal `~` folder earlier releases made stays there). Stores take it or one of its entries; never join `config.root` for data (`config.root` stays for asset roots and configured relative paths). A to-do list left in the backend's old cwd stays there when `RIKO_CONFIG` lies outside `RIKO_DATA_DIR`. `tests/test_data_paths.py` pins every entry to its earlier location in the dev and packaged layouts, so no data moves: add a store there too. A directly built `AppConfig` gets `DataPaths` under its root (its memory files follow), and a `SimpleNamespace` test config needs `paths=DataPaths.at(root)`. Code is located by `app_core/kernel/code_paths.py` `CodePaths` (checkout or frozen bundle, `RIKO_BUNDLE_ROOT`), never the data root: the Discord worker and the tool worker are found there.
- `persistent_memories/` is user data: never delete it during cleanup. Runtime files:
  - `chat_history.json`: the model's context, with one writer: `ConversationHistory` (`app_core/conversation/history.py`, `chat.conversation`). `ChatService` appends a finished turn, `SessionManager` rewrites one (speech over a reply, a cut, a stale redo) through `replace`/`rewrite`, and readers take `snapshot()` (`chat.history` is a copy). Each change is one step under its lock (a leaf below `_voice_lock`) and rewrites the whole file (fsynced) before releasing it; a failed save is logged, not raised, and the next change retries. An unreadable file is kept as `chat_history.json.unreadable-<timestamp>` before anything replaces it. Only a turn still generating or playing is cut by Stop/Sleep/shutdown; failed and cancelled turns keep the user's message.
  - `memory_store.json` (`app_core/persistence/memory.py`): a list of memories (version 1) or `{"version": N, "records": [...]}`, written in the layout it was read in (older builds read only the list) and wrapped only once `STORE_VERSION` is bumped, with a `STORE_MIGRATIONS` step. Unknown keys are kept and written back; a wrongly typed field is read losslessly or reset to its default, logged, and the file as it was (also before a migration) is kept as `.unreadable-<timestamp>` by copy, never by move, before the next save. A newer version or structural damage (bad JSON, a record without text, bad or duplicate ids) fails closed at startup. Its semantic index is an in-memory float32 numpy matrix, re-embedded from record text on every start and never written (FAISS was dropped: its libomp crashed beside torch's on macOS); `memory.index_file` is ignored.
  - `conversations.sqlite3`: the UI archive, built from bus events. It is a second history and can diverge from `chat_history.json`.
  - `tasks.sqlite3` (`app_core/persistence/tasks.py`): revision-checked, and shared with `Code/task_mcp_server.py`.
  - `tool_approvals.json` (`app_core/tools/approval.py`): rules belong to `(source, name)`, so a server's tool never inherits a built-in's rule. A file from before sources (`{name: bool}`) loads as legacy rules, which apply to Riko's tool of that name and, for a server's tool, only as 'ask first'; it is rewritten as version 2 on the next save. A tool without a rule follows its default: `tools.require_approval` for Riko's own, and 'ask first' for an `mcp.json` server's unless that server's entry says `"require_approval": false` (`ToolApprovals.fallback`; the snapshot's `required` is each tool's effective answer, and turning any tool that asks off needs the confirmation). Unreadable or newer files fail closed (every call asks). Each save also writes a top-level `{name: bool}` mirror (ask first when any source asks first), which builds before sources read, so a downgrade fails closed.
  - The whiteboard, desktop, initiative and Discord JSON files, plus `wake_words/`.
- Also under the data root: `logs/debug.log` (rotating, secrets redacted; `configuration/debug_logging.py` redacts the console handler and uvicorn's own handlers too, and `redact_secrets` adds this start's API token and confirmation key once minted), packaged only `logs/backend-launch.log` (the backend's stdout and stderr, written by `release.launchLog` whatever `logging.file_enabled` says: capped at 5 MiB with two backups, this start's secrets redacted), and emotion-probe datasets and weights under `models/` (`app_core/emotion/probe_storage.py`).

### Configuration and settings
- `load_config` (`app_core/configuration/config.py`) reads `$RIKO_CONFIG`, or `./character_config.yaml`, with PyYAML; a missing file silently yields defaults (provider `openai`). Relative paths resolve against the YAML's directory (`AppConfig.root`). Typed dataclasses: `runtime`, `tools`, `memory`, `emotion`, and `voice`, `speech` and `sovits_ping_config` (`AppConfig.voice`/`speech`/`sovits`); other sections are read from `config.raw`. `RuntimeConfig` also declares the background budgets (`initiative_n_ctx`, `initiative_max_output_tokens`, `reflection_n_ctx`), which `load_config` fills from `initiative.*` and `memory.reflection_context_window_tokens`, the keys Settings edits them under. The KV pool is sized only for `llama_cpp`, so other providers never trip over llama-only keys.
- The settings schema (`app_core/kernel/schema.py`): each package registers the sections it reads, a `Section` of `Setting` specs (default, kind, options, editing range, restart scope `none`/`python`/`electron`/`microphone`, live hook, label, help, group, UI section, advanced, `visible_when`, obsolete/hidden) plus hooks: `check` (the section's load-time check), `configure` (checks across sections on the assembled config), `review` and `derive` (Settings-only checks and writes) and cross-field `Rule`s. Owners: `configuration/schema.py` (top level, memory, emotion, tools, tasks, logging, desktop, avatar, presets), `inference/settings.py` (runtime, the llama.cpp checks and KV pool), `kernel/audio_config.py` (voice, speech, sovits), `audio/asr.py` (`voice.asr_*`), `audio/wake_feedback.py`, `animation/library.py`, `emotion/probe.py`, `runtime/initiative.py`. `configuration` imports no feature package: `app_core/__init__.py` imports the declaring modules the first time the registry is read (wherever `load_config` runs), and registers desktop's avatar check. A setting or check declared twice fails at import.
- `VoiceConfig`, `SpeechConfig` and `SovitsConfig` (frozen, in `app_core/kernel/audio_config.py` beside `SAMPLE_RATE`/`FRAME_SAMPLES`) are checked once by their `from_raw`, with the checks in `app_core/kernel/validation.py` that animation and wake feedback share (finite ranges, booleans, choices, text; numeric text passes, since PyYAML reads `1e-3` or a quoted number as a string). A bad value stops `load_config` naming `section.key` (before `desktop.setup_on_startup_error` can help) instead of failing every turn; audio and runtime code reads the fields, never `config.raw` (only ASR's `asr_*` keys still come from `raw`).
- Unknown keys in the strict sections (`voice`, `speech`, `sovits_ping_config`, `animation`, `wake_feedback`, `initiative`, `emotion.probe`: anything no `Setting` or `known` key declares; obsolete settings count as unknown) are ignored and reported in YAML order, never a startup failure: `unknown_settings` logs each once and fills `AppConfig.unknown_settings`, and Settings returns them as `warnings` (snapshot, validate and save, only when non-empty) and marks their fields `unknown`.
- `character_config.yaml` is gitignored and no template is committed. `electron/main.cjs` also parses it at launch and aborts if it is missing.
- The Settings UI goes through `SettingsStore` (`app_core/configuration/settings_store.py`, module-level `LOCK`), with fields and values derived from the schema:
  - GET returns values, fields and a sha256 `revision` (no config path). A secret (`schema.secret`: a last name that is, or ends in `_` and, `api_key`, `token`, `password`, `passphrase` or `secret`; never `*_tokens`) is never sent: one the YAML holds comes as `SECRET_MASK` with `secret_state: 'saved'`, one from elsewhere (`RIKO_API_KEY`, a legacy top-level key) as `''` with `secret_state: 'external'`; on validate, save and the resource estimate the mask means keep (`kept()`), `''` clears, and comparisons use `stored_values()`. Derived path values (`memory.store_file`, ...) and the path check's `resolved` are still absolute, so the data root's location reaches the renderer (accepted: the renderer is the user's own UI). `/api/settings/path` takes `{key, value}` for a file or folder setting only, checks the value as text first (`local_path`) and runs `which` only for a bare command of an `*executable` setting. GET also returns `rules` (cross-field checks the backend also enforces, e.g. `n_ubatch <= n_batch`) and `restart_pending` (`{path: scope}` for saved settings that differ from the config the running backend loaded; `restart_required` is true when any is). Each field also has `restart_scope`, and runtime keys a provider-specific `visible_when` (every provider's keys are sent). The renderer takes all three from there (`electron/src/settings_model.mjs`: `shownFields`/`fieldRelevant`, `ruleErrors`, `restartNotice`/`pendingRestart`); group and section order stay in `settings_page.jsx`. `electron/src/settings_contract.json` holds the rules and sample cases both languages must judge alike (`tests/test_electron_settings.py`): copy `schema.rules()` into it when a rule changes.
  - Validate writes a temporary `.settings-validation-*.yaml` beside the config, runs `load_config` on it, then each section's `review` hook (wake word, speech recognition pair, avatar, live budget) and `derive` hook (the automatic KV pool it writes). `validate_file()` checks a whole file the same way, as if every offered value were edited, on what PyYAML reads (`--validate-config`, the first run).
  - PUT re-checks the revision (409 on conflict), keeps `character_config.yaml.previous` (owner-only, through `atomic_write(mode=0o600)`), and writes via mkstemp + fsync + `os.replace`. ruamel preserves comments and unknown keys.
- Only keys already in the YAML or listed by a `Setting` default are editable; a `Setting`'s kind (else the value's), and a numeric default's type, decide the form. To add a setting, register one `Setting` in the section of the module that reads it (and read or check it there); a default lists it in Settings. To apply it on save, give it `restart='none'` and a `live` hook name and add that hook to `LIVE` in `app_core/http/settings.py` (a hook takes the Backend, the saved values and the changed paths; `tests/test_desktop_api.py` checks they match).
- Applied live (restart scope `none`): `avatar.*`, `runtime.pause_background_on_live`, and `emotion.probe.interval_tokens` (if the probe was enabled at load); the initiative budgets also reach the running initiative, but the KV pool needs a restart. Electron reads `desktop.shortcuts`, `desktop.debug` and the name (`presets.default.name`, else `character_name`) only at launch (scope `electron`), through `electron/launch_config.cjs`. Everything else needs a Python restart. `persistent_memories/initiative_settings.json` overrides the YAML `initiative` section.
- The backend's PyYAML parses YAML 1.1 and ruamel (Settings' round trip) 1.2; they disagree on `yes`/`no`/`on`/`off`. `electron/launch_config.cjs` is Electron's one reader of the YAML: the `yaml` package narrowed to PyYAML's resolvers (booleans, `017`, `1:30`, but `y`, `09` and `1e3` stay text; a repeated key keeps its last value), checked against PyYAML by `tests/test_electron_settings.py`. Anything else Electron reads from the YAML goes through it.

### Electron ↔ backend contract
- One backend origin: `electron/backend_origin.cjs` alone names the default `http://127.0.0.1:8765` (`src/backend_origin.test.mjs` fails on the port anywhere else under `electron/`). Main resolves it once in `whenReady`: dev from `RIKO_BACKEND_URL` (only `http://127.0.0.1:<port>`), packaged as a free port (`release.freePort`) passed to the spawned backend as `RIKO_PORT`. Every window gets it as a `--riko-backend=` argument (`rendererPreferences` in `main.cjs`, `webPreferences.additionalArguments`) that the sandboxed preload exposes synchronously as `rikoConfig.backend`; `src/api.mjs` derives `API`, `EVENTS`, `socketURL` and `mediaURL` from it, and its `request()` is the renderer's only `fetch` (JSON or a typed binary `body`; errors carry the backend's detail, or raw text, and `status`). CORS allows `null` (the packaged `file://` renderer) and the Vite origin; the Host guard ignores the port. `electron/index.html` carries a meta Content-Security-Policy (`src/content_security.test.mjs` pins it): scripts and styles from the bundle only, and loads only from the page itself, `data:`/`blob:` where the VRM loader, KaTeX and the logo need them, and `http://127.0.0.1:*`/`ws://127.0.0.1:*` (a meta tag cannot know the dynamic backend port; `backend_origin.cjs` admits only `127.0.0.1`); `vite.config.mjs`'s `devCsp` adds Vite's `ws://localhost:*` HMR socket while it serves. FormattedText never loads a remote image: an http(s) Markdown image becomes a click-to-open link and a local one goes through `/api/media` (`imageSource` in `format_text.mjs`).
- Every HTTP and WebSocket request needs `Authorization: Bearer <token>` and a loopback Host; WebSockets also need an app Origin (`LocalAPIGuard` in `app_core/desktop/api_guard.py`). The token and a separate confirmation key are fresh on every backend start, minted only after `run_server.py` has bound its port (before the model loads), and removed from the backend's environment so children never inherit them:
  - Packaged: Electron generates both and passes `RIKO_API_TOKEN`/`RIKO_CONFIRM_KEY` to the backend it spawns; nothing is written to disk. Main sends the token only after the backend prints `RIKO_BACKEND_LISTENING port=<the port main gave it>` on stdout (`watchListening`/`listeningLine` in `electron/release.cjs`), and stops when it exits.
  - Dev: the backend writes `persistent_memories/api_token` and `confirm_key` (mode 0600) beside the config; Electron main re-reads them when they change.
  - Electron main injects the header for every renderer request to the backend origin and no other (`injectToken` in `backend_supervisor.cjs`, `ownsRequest`), so renderer code never handles the token; main's own requests use `backend.request` (the only `fetch` in main-process code, a guard in `src/backend_origin.test.mjs`). The Discord worker gets `RIKO_API_TOKEN` and `Discord_backend_url` (this backend's port, outranking the `.env`) from its launcher and exits when its stdin pipe closes, i.e. with that backend (`RIKO_EXIT_WITH_BACKEND`); started by hand, `client_token()` reads the file on every reconnect (`api_guard.issue_secrets` writes `DataPaths.api_token`/`confirm_key`). Use `127.0.0.1`, not `localhost`, which may resolve to `::1`.
  - Tests use `client_for(backend)` from `tests/conftest.py`. API docs are served only with `RIKO_DEV=1`.
- Security-sensitive changes (`security_sensitive()` in `app_core/http/settings.py`, challenged by `Backend.require_confirmation`: anything that loads code, models or libraries, starts programs, widens file access or sends data elsewhere, judged by key name, by every leaf of a section saved at once, and by values that are URLs or absolute paths; turning tool approval off; Discord access) return 428 with a single-use `confirm` challenge. `request()` in `electron/src/api.mjs` asks Electron main (`confirm-security-change`), which shows a native dialog and signs the challenge with the confirmation key, which never goes over the wire. A secret's new value is in the challenge (and the dialog) only as `new secret, sha256 <16 hex>` (`shown()` in `http/settings.py`), which still binds the approval to it. A new setting that can do any of those things must be covered by `security_sensitive()`.
- `/ws/events` (`app_core/events/stream.py`) sends `state.snapshot`, then `resource.snapshot`, then every bus event. A client with 100 queued events is closed with code 1013.
- All windows share one socket (`electron/src/event_connection.mjs`, 1 s reconnect). Subscribe via `connectEvents`, `useRuntime` or `useResource`, and never poll: `electron/src/subscription_guard.test.mjs` forbids `setInterval`.
- `DesktopState` (`app_core/desktop/state.py`) is a thin facade over components sharing one `DesktopEvents` (`desktop/listeners.py`): `WhiteboardModel` (`whiteboard.py`: commands, pages, clear, acknowledgements, `whiteboard.json`), `SurfaceGeometry` (`geometry.py`: avatar/whiteboard geometry, displays, `desktop_settings.json` through the `atomic_write` the factory passes, so `desktop/` imports nothing from app_core but `kernel`), `EffectsModel` (`effects.py`), `PlaybackFlags` and `Presence` (`presence.py`: mic/audio/volume/sleep; speech bubble and emotion) and `ActivityLog` (`activity.py`: tools, actions, notifications, incoming, Discord status; `ToolRegistry`'s `activity=` and `DiscordLauncher`'s). Each owns its lock and emits after releasing it; `snapshot()` takes each lock in turn (`SNAPSHOT_KEYS` fixes the payload's keys and order). Code outside `desktop/` uses only their public methods (`set_displays`, `record_action`, `save_avatar_geometry`, `set_mic`, ...); `get_desktop_state()` is a transitional process-wide fallback for a tool built without services, not the backend's state. Every desktop change republishes a full `state.snapshot`. Panels read `resource.<topic>` events from `ResourceEvents` (`app_core/events/resources.py`), which computes each on its own `DaemonExecutor` worker, never the publisher's thread (a publisher may hold a component lock), so the update follows its trigger on the socket; a topic already waiting there is not queued twice. A new topic needs an `observe()` mapping and a domain getter in `Backend.resource_getters()` (not a route function; it raises `ResourceUnavailable` when the feature is off, which routes answer with 503 and the bridge logs at debug). `tests/test_desktop_api.py` pins every route's path and methods (`ROUTES`).
- `POST /api/chat` returns only after the full reply; deltas arrive over the socket. Renderer acknowledgements are authoritative (`/api/surfaces/result`, `/api/avatar/animation/result`).

### Discord
`Code/discord_bot.py` is a separate process and only a backend client; it loads no model. A failed Discord send or edit costs only that chunk (`StreamReply` retries it on the next flush with the same per-chunk nonce, so Discord never posts it twice; `finish()` is idempotent), and the turn queue survives transport errors and is restarted by a done-callback if it ever dies. It holds one WebSocket at `/ws/discord/client?instance=<uuid>`, which carries only the events `bot.py` handles (`client_event_filter` in `app_core/integrations/discord/api.py`: its own turns' deltas, reasoning and approval requests, approvals, Discord and whiteboard resources, initiative messages), and calls `/api/discord/*`; every Discord route, the socket included, is in `create_router` (`app_core/integrations/discord/api.py`), which reads the session, the launcher, the confirmation (`confirm`, required with a launcher), the resource snapshot and the bus through the accessors `create_app` passes. Start it with `POST /api/discord/start` or the tray menu, or by hand once the backend runs. The launcher starts `CodePaths`' worker with `RIKO_DATA_DIR` and an absolute `RIKO_CONFIG`, and the worker takes its `.env`, `discord_access.json` and `discord_preferences.json` from the `DataPaths` of that config, so it uses the backend's files even when the two variables name different folders. Credentials go in a local `.env` (template: `.env.discord.example`).

### Dev vs packaged
- **Dev:** the repo root is both the cwd and the data root.
- **Packaged, first launch:** Electron shows `#/setup`. `saveSetup` (`electron/release.cjs`) keeps the data folder's rules (absolute, outside the install folder), runs `riko-backend --setup-config <data>` with the choices as JSON on stdin (`app_core/configuration/first_run.py`: the choices over what a packaged build starts with, rendered by PyYAML and checked with `validate_file()`), writes the answer to `<data>/character_config.yaml` (never overwriting) and records `data-location.json` in Electron's userData. A refusal shows on the setup page.
- **Packaged, later launches:**
  - Electron spawns `backend/riko-backend` with `RIKO_MANAGED=1`, `RIKO_PORT` (a free port), `RIKO_DATA_DIR`, `RIKO_CONFIG` and `RIKO_BUNDLE_ROOT`.
  - Hugging Face and torch caches go under `<data>/models`.
  - A `shutdown` line or EOF on stdin stops the backend (it dumps stacks and exits itself after 14 s); Electron sends SIGTERM after 15 s and SIGKILL 3 s later. On macOS the backend's PATH gets the Homebrew prefixes so MCP servers and ffmpeg resolve (`finderPath`).
  - `runtime.native_library: bundled:<cuda|vulkan>` resolves to `$RIKO_BUNDLE_ROOT/native/<backend>/`.

## Conventions and gotchas
- Whole-file JSON writes go through `persistence/atomic.py` `atomic_write`: a unique temp file beside the target, fsync (`F_FULLFSYNC` on macOS), `os.replace` retried briefly on `PermissionError` (Windows sharing violations from antivirus or indexers), then a best-effort directory fsync; new files are 0600, and temporaries older than 10 minutes (left by a killed process) are swept. `persistent_memories/` is gitignored at any depth except the checkout's README, as are the data root's other user files (`mcp.json`, `.env.*`, `models/`, `character_files/*` except the tracked `main_sample.wav`, a literal `~/` task store) and the copies of the YAML that may hold keys (`.previous`, the settings and estimate temporaries, at any depth); `tests/test_repository_hygiene.py` checks that no tracked file is ignored. `atomic_write(mode=...)` sets the permission bits whatever the old file had. The settings YAML, the API secrets and the whiteboard keep their own writes. Stores fail closed rather than resetting user data: keep an unreadable file with `persistence/preserve.py` (`<name>.unreadable-<timestamp>`), or refuse to save over it.
- A workflow download needs a recorded SHA-256 checked before use, a new `uses:` a full commit SHA with its tag in a comment, and code fetched at runtime a pinned commit (`kernel/model_pins.py`).
- Optimistic concurrency uses revisions throughout: the settings `revision`, task `expected_revision` (`TaskConflict` → 409), the Discord access revision, memory-record revisions, and whiteboard `board_revision`.
- Every path from the renderer, the model or a settings form is checked as text before any filesystem call (`app_core/kernel/safe_paths.py`; on Windows resolving or stat-ing `\\host\share` contacts the host and offers the user's credentials): `lexical` refuses network and device paths and Windows' ambiguous forms, `within` checks containment, `resolve_within` then resolves and re-checks the real path (no symlink out), and `local_path` is for a file the user chose anywhere on this computer (imports, the Settings path check, and a draft's paths before `/api/resources/estimate` stats them). Reserved device names are judged as Win32 does (the name before its first `.`, trailing spaces removed: `COM1 .png`). Media goes through `resolve_media` (`app_core/desktop/media.py`: approved roots under the data root as given and as resolved, plus an extension allowlist).
- Heavy dependencies (torch, faster_whisper, sounddevice, silero_vad, sentence_transformers, openai, huggingface_hub) are imported lazily, and tests swap them through `sys.modules`. Services accept `start=False` / `start_worker=False`. Tests must close services and unsubscribe from the global `event_bus` in `finally`.
- The `app_core/` root may contain only `__init__.py` and `factory.py`, and every relative import must resolve (`tests/test_app_core_structure.py`). `app_core/__init__.py` is a lazy facade (PEP 562): its public names load on first use, so a leaf import (a store, the tool worker, `task_mcp_server.py`) loads only what it uses. Inside app_core, import from the defining module, never the facade, `factory.py` or an entry point.
- `app_core/kernel/` holds the leaf utilities every package uses (messages, streaming, output_filter, cancellation, workers, lifecycle, metrics, torch_device, background_budget, code_paths, safe_paths, model_pins) and imports nothing else from app_core. The old paths (`conversation/messages.py`, `runtime/workers.py`, ...) are re-export shims for one release, listed in `SHIMS` in `tests/test_app_core_structure.py`. `tests/test_package_boundaries.py` pins every cross-package import, module-level or inside a function, in `EDGES` and forbids cycles: a new edge fails until it is added there, and a vanished one until it is removed.
- Tools (`app_core/tools/`) share one `Tool` shape (`tool.py`: name, description, input_schema, `choices(arguments)`, `prepare`, `execute`, plus `isolated`, `read_only`, `owner` and `source`) and all enter through `ToolRegistry.register(tool, *, source, replace=False)`: `register_local` adapts built-in and desktop tool objects, `register_mcp` an MCP client's tools, and SessionManager registers its own tools the same way. `source` is `RIKO` for Riko's own tools, whose names must match `^[a-zA-Z0-9_-]{1,64}$` and never clash (a clash raises), or `mcp:<server>` for an `mcp.json` server, whose tool runs as `<server>__<name>` (warning logged) when its name is invalid or taken, even by one of Riko's tools registered later, and is left out when that fails too. Built-ins run in an isolated subprocess because `BaseTool.ISOLATED` says so (`isolation.py`), not because of their module path; desktop tools run in-process and their `execute` signature is their schema. Tool-specific input rules stay in the tool (`choices(arguments)` leaves out what a call need not choose). The initiative check offers exactly the `read_only` tools; only Riko's own can be (TaskMCP's `readOnlyHint` marks `task_list` and `task_get`), never a server's. `registry.py` is policy only: schemas are `schema.py`, the stdio and HTTP transports `mcp/`, and the old names stay importable from `registry.py` for one release. `ToolRegistry.execute` waits in slices so Stop ends a call at once: it kills that call's worker, or sends a stdio MCP server `notifications/cancelled`, and returns an error result. `mcp.json` (copied from `mcp.json.example`) loads only if `tools.mcp_config` points at it. A stdio server starts with a minimal environment (`server_environment` in `mcp/stdio.py`: the MCP SDK's safe set, `RIKO_DATA_DIR`/`RIKO_CONFIG`, the names its entry lists in `inherit_env`, then its `env`), never the backend's keys and tokens; a server's tools ask before each call unless its entry says `"require_approval": false` (a value that is not a boolean keeps the server from loading); and the model gets a server's descriptions (capped) and results and failures (JSON-encoded; a JSON-RPC error or any exception its call raises, under `error`) framed as untrusted, with the server and tool names quoted (`untrusted_description`/`untrusted_output` in `mcp/__init__.py`), while the activity panel keeps the raw result. Its input schema is capped once at registration (`untrusted_schema`: every string value to 256 characters, lists to 128 items, nesting to 16 levels; property names stay whole), and a tool whose capped schema is still over 32 KiB of JSON is left out with a notice. `ToolRegistry` reports tool activity and MCP load failures to the observer it is given (`activity=`; the factory passes the desktop's `ActivityLog`), never the desktop singleton, and registers the local tools it is given after the built-ins and before the MCP servers (`local_tools={owner: tools}`): the factory passes the desktop tools, built over its `DesktopServices` (media resolver, effect library, gestures, walking), so `tools/` imports nothing from `desktop/`.
- `tools.disabled` (a list of tool names) keeps tools out of the registry entirely: never offered, never run, and their descriptions no longer cost prompt tokens on every turn.
- Electron:
  - Pure logic lives in `.mjs`/`.cjs` files, each with a sibling `*.test.mjs`.
  - Main-process tests are behavioural: `src/electron_fakes.mjs` records a fake Electron (and manual timers), the modules are tested against it, and `src/main_wiring.test.mjs` evaluates the real `main.cjs` and `preload.cjs` against it (startup order, token gating, setup, quit, every channel's owners). Only guards and a few CSS and component checks still read source text (the default port, `fetch`, `setInterval`, morph.css, some JSX), so refactors there must update them. StreamChat's event handling is `src/stream_chat_reducer.mjs`.
  - `electron/vite.config.mjs` passes `react` without calling it, so JSX uses the classic transform and every `.jsx` must `import React`.
- Style: the Python and JS are dense, often with several statements per line; match the surrounding code.
- The README links to `docs/*.md`, but `/docs` is gitignored and absent.
- `tools/migrate_legacy_memories.py` and `tools/migrate_legacy_chat_history.py` only dry-run unless given `--write`; run them with the app stopped.

## Platform status

Releases ship CUDA and Vulkan bundles for Windows and Linux x64 and a Metal bundle in an arm64 macOS DMG (macOS 14+, ad-hoc signed unless the MAC_* signing/notarization secrets exist). ROCm/HIP is an opt-in Linux bundle (`hip`, release.yml's `hip` input) that links the user's ROCm 7; rocm-compile.yml (started by hand: twelve GPU targets take hours) compiles it in the ROCm container and loads it there without a GPU, which is all that proves it: it has never run a model on an AMD GPU. The Python inference layer is backend-agnostic: the backend is whatever llama.cpp build `runtime.native_library` loads, or whatever llama-server `runtime.provider: llama_server` talks to (any backend, without the emotion probe; checked against stock llama-server b11408 on Apple Silicon). The patched bridge, including the emotion probe, has been built and run on Apple Silicon Metal at the current pin.

Backend and device assumptions live here:
- **Native build and packaging:**
  - `electron/native_backends.json` is the one manifest of backends (cuda, hip, vulkan, metal), the platforms that ship each, per-OS library names (`riko-native.dll`, `libriko-native.so`, `libriko-native.dylib`), shared-library patterns, rpaths (`$ORIGIN`, `@loader_path`) and CMake switches. cuda and vulkan add `-DGGML_BACKEND_DL=ON -DGGML_CPU_ALL_VARIANTS=ON` (as upstream's x64 releases), so ggml's backends ship as modules with one `ggml-cpu-<isa>` per x86 level and x86 CPUs without AVX2/FMA/F16C/BMI2 no longer hit SIGILL; metal stays linked (as modules it would need a `.so` darwin pattern, which the manifest validator demands). Only CI and real hardware prove the x86 GPU modules and variant pick; the loader was verified with a Metal `GGML_BACKEND_DL` build (Apple variants) and a Linux arm64 CPU-module bundle. hip is `optional` (`release_backends` leaves it out; `bundled:hip` still resolves on Linux), with an explicit `GPU_TARGETS` (CDNA gfx908-gfx950, RDNA2 gfx1030, RDNA3/3.5 gfx1100-gfx1151, RDNA4 gfx1200/gfx1201; the notes say why), an extra rpath (`/opt/rocm/lib` after `$ORIGIN`) and `system_libraries` (libamdhip64, hipBLAS, rocBLAS: never bundled). Detection may list `fallbacks` (argv) and a `pattern` (rocminfo lists the CPU too). `app_core/configuration/native_backends.py`, `electron/native_backends.cjs`, `config.py` (`bundled:<backend>`), `release.cjs` (hardware detection runs only the detect commands of the bundles installed under `resources/native`: none on macOS; an optional bundle is offered only when its required detection found hardware, so HIP needs an AMD GPU with ROCm and Vulkan stays the AMD default) and `first_setup.jsx` (which says why a bundled optional backend is not offered) read it; naming is tested with explicit per-platform tables on every host.
  - `tools/release/build.py` builds the manifest's default backends for the host OS (plus prebuilt optional ones from `RIKO_OPTIONAL_BUNDLES`; `RIKO_BUILD_JOBS` overrides `-j 2`), keeps versioned library symlinks, renders the macOS icon from `assets/logo.svg`, puts `Code/` on PyInstaller's path (without it `--collect-submodules process` silently froze none of Riko's dynamically imported modules) and repeats `--release-check` inside the packaged app (`--check-app`).
  - `.github/workflows/release.yml`: windows-2022 and ubuntu-22.04 (CUDA 12.4.1, Vulkan) and macos-15 (Metal DMG); with the `hip` input, a `hip` job in `rocm/dev-ubuntu-22.04:7.2.1` (pinned by digest, shared with rocm-compile.yml) that all legs wait for, and `-hip` Linux packages.
  - `electron/electron-builder.yml`: NSIS, AppImage, deb and a hardened-runtime mac dmg with `electron/build/entitlements.mac.plist` (allow-jit, audio-input, disable-library-validation, each needed by V8, the microphone or torch) and the `electron/build/mac_sign.cjs` signing hook. Packaged macOS asks for microphone access before starting the backend. No Windows signing is configured (`tools/release/README.md`, Code signing).
- **Library loading:** `os.add_dll_directory` is called only on Windows (`app_core/inference/llama_native.py`, `Code/run_server.py`); the bridge loads `GGML_BACKEND_DL` modules from its own folder on every OS (`riko_load_backends` in `riko-native.cpp`); `ggml-hip` finds ROCm through its `/opt/rocm/lib` rpath or the loader's path (distribution ROCm).
- **GPU telemetry:** `app_core/resources/gpu_sources.py` reads, per sample, nvidia-smi when on PATH (any OS; compute processes only, so attribution stays incomplete), on Linux the amdgpu sysfs VRAM counters and the DRM fdinfo of Riko's own processes, on Windows every hardware DXGI adapter (any vendor, PCI address from D3DKMT) with PDH's GPU Adapter/Process Memory counters by their English names (one kept query, no PowerShell), and last the bridge (`provider.devices()`); `gpu_memory.merge` joins them into one row per GPU by PCI address, else UUID or LUID (a field takes the first source's value, so device-wide vendor figures win and ggml's fill gaps, except an integrated GPU's memory: ggml's shared pool, what llama.cpp budgets, replaces the vendor's carve-out, and its vendor process lists count as incomplete; a ggml free above total is unknown), with `key`, `memory_kind` (`unified` for Metal and integrated GPUs) and `memory_scope` (`process` for Metal: used is this Python process's working set, `owned_mib` all of it, Other unknown) and `main_key` (llama.cpp's main device). macOS has no source but the bridge (an older `.native/metal` without `riko_devices` reports nothing). `process_identity` uses /proc, `GetProcessTimes` or libproc. `vram_estimate.target_gpu` maps `runtime.main_gpu` (a llama.cpp device index) to a row through `inference/devices.model_devices` (llama.cpp's default device rule at the pin: re-check it when the pin moves), sums the rows a split model spans (`draft_telemetry` drops the device list when a draft loads another native library or provider than the running one, whose numbering it is), and in unified process scope projects against the working set with no reserve for other processes (no projection with `n_gpu_layers` 0), while its context suggestion is capped at 75% of RAM with Electron reserved; the Python torch models get rows from their resolved devices (Julia maps MPS to the CPU; an unresolved `auto` on macOS is MPS or the CPU, never a CUDA context).
- **ASR:** every faster-whisper model is built by `app_core/audio/asr.py:create_whisper`, and the session keeps one (`AsrService`). Defaults are `auto`/`default`, resolved from what CTranslate2 reports (CPU int8 on macOS, which has no CTranslate2 GPU backend); an unsupported configured pair falls back once with a warning, and Settings refuses one when it is edited. GPU ASR on Metal or ROCm needs a different engine (whisper.cpp, mlx-whisper, or a HIP-built CTranslate2).
- **Torch devices:** `app_core/kernel/torch_device.py` accepts `auto`/`cpu`/`cuda[:n]`/`mps` (ROCm torch reports `cuda`). Julia maps `mps` to CPU until upstream moves inputs for MPS, retries a failed GPU load on CPU, and restores torch's thread count after loading. `memory.device` covers the memory classifier and embedder; `DEVICES` in `configuration/schema.py` and `tests/test_llama_native.py` pin the lists.
- **Computer awareness:** `app_core/runtime/activity.py`: `WindowsActivity` (GetLastInputInfo, foreground window title and PID), `MacActivity` (CoreGraphics idle time without a permission prompt; the frontmost app's name, bundle ID and PID from `lsappinfo`, never window titles, which need Screen Recording), `LinuxActivity` (idle over D-Bus through `gdbus`: Mutter IdleMonitor, else org.freedesktop.ScreenSaver, in milliseconds on KDE; unsupported only when gdbus answers ServiceUnknown/UnknownMethod for both, asked again after 60 s, while a timeout is a passing error; the active X11 window through `xprop`; nothing on Wayland) and `NullActivity` elsewhere. `capabilities()` makes only static checks; Initiative samples only the fields that are both allowed and supported, one call per field, and its snapshot carries `capabilities` and `perception` (`off`/`unsupported`/`waiting`/`available`/`error`, from the last sample), which the session's runtime observation and `electron/src/initiative_model.mjs` use; the tool loop compares observations without any `observed_at` and with idle time by the minute (`chat.observation_state`). Only hardware proves these beyond the faked tests.
- **Windows-only behaviour:** the Win32 pointer hooks in `electron/window_platform.cjs`, and the acrylic material in `electron/window_material.cjs` (applied through `window_platform.cjs`).
